# TLS Certificates for Self-Hosted Teleport

How to go from *nothing* to a **verified, working certificate chain** for a
self-hosted Teleport cluster: generate the CSR, get it signed (public CA or
corporate PKI), find the intermediates, obtain the root, and prove the chain
is correct **before** it goes anywhere near the cluster.

Everything here is cluster-agnostic — it feeds the same `teleport-tls`
Kubernetes secret whether you deploy the local
[quickstart](01-quickstart/), [OpenShift](03-openshift/), or a cloud
provider.

The worked example uses `teleport.example.com`. Substitute your cluster name.

---

## 0 — Decide the names first

[The one rule](README.md#the-one-rule-that-makes-or-breaks-the-install):
**the Teleport `clusterName`, the DNS name clients resolve, and the
certificate SANs must all be the same string** — and the name is permanent.

You need **two** names in the certificate:

| SAN | Why |
|---|---|
| `teleport.example.com` | The cluster name — web UI, tsh, API, everything |
| `*.teleport.example.com` | Application Access serves every app at `<app>.teleport.example.com` |

Modern clients only look at the SAN list — a name that is only in the CN
does not count.

---

## 1 — Generate the private key and CSR

The private key is generated by you and **never leaves your machine** — the
CA only ever sees the CSR (a signed statement of your public key + requested
names).

Use a config file so the SANs are embedded in the CSR itself. **The CN is
the wildcard** — public CAs key their wildcard activation flow off the
CSR's CN, so a base-name CN gets your order treated as a single-domain
cert (Namecheap, for one, will refuse to add the wildcard later):

```bash
cat > teleport-csr.cnf <<'EOF'
[req]
distinguished_name = dn
req_extensions     = req_ext
prompt             = no

[dn]
CN = *.teleport.example.com

[req_ext]
subjectAltName = DNS:*.teleport.example.com, DNS:teleport.example.com
EOF

openssl req -new -newkey rsa:2048 -nodes \
  -keyout teleport.example.com.key \
  -out teleport.example.com.csr \
  -config teleport-csr.cnf
```

(The file names stay wildcard-free — `*` in filenames is asking for shell
trouble. For a **corporate PKI** request, ask your PKI team which CN form
their template expects — base name or wildcard; either is fine as long as
both SANs end up in the issued cert, which is what Step 3 checks.)

Verify the CSR **before** submitting it — CN and both SANs:

```bash
openssl req -noout -text -in teleport.example.com.csr | grep -E "Subject:|DNS:"
```

Expected:

```
        Subject: CN=*.teleport.example.com
                    DNS:*.teleport.example.com, DNS:teleport.example.com
```

> **RSA 2048?** Universally accepted by public and corporate CAs alike.
> ECDSA P-256 also works with Teleport if your CA supports it.

Guard the key:

```bash
chmod 600 teleport.example.com.key
```

## 2 — Get it signed

### Path A — Public CA (Namecheap, DigiCert, …)

1. **Buy a product that covers both names.** A **wildcard** certificate for
   `*.teleport.example.com` is the usual answer — issuers bundle the base name
   (`teleport.example.com`) into the SAN automatically, but *verify before you
   buy*. A multi-domain/SAN certificate also works only if the product
   allows a wildcard entry in a SAN slot (plain SAN products often don't).
2. In the activation flow, choose **manual CSR** ("Manage SSL manually" on
   Namecheap), paste the CSR — the primary domain prefills from the CN.
3. Complete **domain-control validation**. Wildcards require DNS validation:
   the CA gives you a TXT or CNAME record to publish in the `example.com` zone.
   Issuance follows minutes after the record propagates.

> **Public CAs generally take the certificate's names from the order form,
> not from the CSR's SAN extension** — each name must be validated
> individually. The CSR SANs don't hurt, but what matters is what you enter
> (and validate) in the portal, and what's in the *issued* cert (Step 3).

You'll get back a leaf certificate (e.g. `teleport_example_com.crt`) and usually
an intermediate bundle (Namecheap: `teleport_example_com.ca-bundle`).

### Path B — Corporate / internal PKI

Submit `teleport.example.com.csr` to your PKI team and request:

- a **TLS server certificate** (Extended Key Usage: `serverAuth`),
- issued **with the SANs from the CSR honored** — say this explicitly.
  Some PKI systems (including default Microsoft ADCS templates) silently
  ignore CSR SANs and issue CN-only certificates. A CN-only cert **will not
  work** — clients ignore the CN.

Ask for the **issuing chain** at the same time: every intermediate CA
certificate between your cert and the root, plus the root itself. PKI teams
have these on hand; getting them now saves the archaeology in Step 4.

> With a corporate PKI, the cluster install itself needs **no CA secret** —
> but the corporate **root** must be in the OS trust store of every machine
> that connects: workstations (browser + tsh) *and* every node you enroll.
> On corporate-managed devices it usually already is.

## 3 — Inspect what came back

Never assume the CA issued what you asked for:

```bash
openssl x509 -noout -subject -issuer -dates -ext subjectAltName \
  -in teleport_example_com.crt
```

Check all four:

- **subject** — your name (`CN=teleport.example.com` or `CN=*.teleport.example.com`)
- **issuer** — the CA that signed it (you'll chase this in Step 4)
- **dates** — currently valid (`notBefore` in the past, `notAfter` in the future)
- **Subject Alternative Name** — **both** `teleport.example.com` and
  `*.teleport.example.com` present. If either is missing, stop and get the
  certificate reissued. Nothing downstream can fix a missing SAN.

Also confirm the cert matches your private key — the public-key hashes must
be identical:

```bash
openssl x509 -noout -pubkey -in teleport_example_com.crt | openssl sha256
openssl pkey -pubout -in teleport.example.com.key | openssl sha256
```

---

## 4 — Find and verify the intermediates

Your leaf is almost never signed directly by a root. There are one or more
**intermediate CAs** in between, and clients can only build the chain if you
serve those intermediates alongside the leaf. A missing intermediate is the
single most common certificate failure: browsers often paper over it (they
cache intermediates), while `tsh`, `curl`, and enrolling nodes fail with
`certificate signed by unknown authority`.

> **Corporate PKI fast path:** your PKI team handed you the intermediates
> and root in Step 2 — skip the AIA archaeology below and jump straight to
> the link-verification commands (issuer/subject and AKI/SKI), then to
> Step 5's `openssl verify`.

**If the CA gave you a bundle** (`.ca-bundle`, "intermediate certificates",
or the PKI team's chain file), use it — but still verify it below.

**If you only have the leaf**, walk the chain yourself using the
**Authority Information Access (AIA)** extension — nearly every certificate
embeds the URL of its issuer's certificate:

```bash
openssl x509 -noout -text -in teleport_example_com.crt \
  | grep -A2 "Authority Information Access"
#   CA Issuers - URI:http://crt.sectigo.com/SectigoRSADomainValidationSecureServerCA.crt
```

Fetch it (issuer certs are usually served in DER; convert to PEM):

```bash
curl -sfo issuer.der "http://crt.sectigo.com/SectigoRSADomainValidationSecureServerCA.crt"
openssl x509 -inform der -in issuer.der -out intermediate-1.crt 2>/dev/null \
  || cp issuer.der intermediate-1.crt   # some CAs serve PEM already
```

Now repeat on `intermediate-1.crt`: print its issuer and its AIA, fetch the
next cert up, and so on. **Stop when you reach a certificate whose subject
equals its own issuer** — that's the root (roots have no AIA; they are
self-signed by definition).

At each hop, verify the link actually connects — the child's *issuer* must
equal the parent's *subject*:

```bash
openssl x509 -noout -issuer  -in teleport_example_com.crt
openssl x509 -noout -subject -in intermediate-1.crt
# These two lines must be the same DN
```

Belt-and-suspenders: the child's **Authority Key Identifier** must equal the
parent's **Subject Key Identifier** (this catches same-name/different-key CA
generations, which corporate PKIs love):

```bash
openssl x509 -noout -ext authorityKeyIdentifier -in teleport_example_com.crt
openssl x509 -noout -ext subjectKeyIdentifier   -in intermediate-1.crt
# The hex strings must match
```

If you collected more than one intermediate, concatenate them child-first:

```bash
cat intermediate-1.crt intermediate-2.crt > intermediates.crt
```

## 5 — Obtain the root and verify the full chain

The **root** is your verification anchor. Get it from a trustworthy place —
the CA's official download page, your OS trust store, or your PKI team —
**not** from the same untrusted channel as the leaf (verifying a chain
against a root that came bundled with it proves nothing).

For a public CA, confirm the root is genuinely in your OS trust store:

```bash
# macOS
security find-certificate -a -c "USERTrust RSA Certification Authority" \
  /System/Library/Keychains/SystemRootCertificates.keychain
# Linux
awk -v cmd='openssl x509 -noout -subject' '/BEGIN/{close(cmd)}{print|cmd}' \
  /etc/ssl/certs/ca-certificates.crt 2>/dev/null | grep -i usertrust
```

Now the money command — cryptographic proof that leaf → intermediates → root
is one unbroken chain:

```bash
openssl verify -CAfile root.crt -untrusted intermediates.crt teleport_example_com.crt
```

The only acceptable output:

```
teleport_example_com.crt: OK
```

- `unable to get local issuer certificate` → an intermediate is missing or
  the wrong one (recheck the AKI/SKI pairs from Step 4)
- `certificate has expired` → check *which* cert expired; intermediates
  expire too
- `self-signed certificate in certificate chain` → you put the root in
  `-untrusted`; it belongs in `-CAfile` only

> `-untrusted` is openssl's (confusing) name for "intermediates that don't
> need to be independently trusted" — exactly the role they play in real TLS.

---

## 6 — Assemble the chain file

Servers must send the leaf plus all intermediates, **leaf first**, in
issuing order. The root is **omitted** — every client already has it (that's
what makes it a root):

```bash
cat teleport_example_com.crt intermediates.crt > chain.crt
```

Sanity-check the order — first cert must be your name, each subsequent
subject must be the previous issuer:

```bash
openssl crl2pkcs7 -nocrl -certfile chain.crt \
  | openssl pkcs7 -print_certs -noout
```

> **Check your CA bundle for a stowaway root.** Some CAs (SSL.com via
> Namecheap, for one) ship a `.ca-bundle` that contains the intermediates
> **and the root** — sometimes in server-hostile order. Inspect it with the
> same `pkcs7 -print_certs` command: the cert whose subject equals its own
> issuer is the root. Strip it; if it's the last block, the first N blocks
> are your intermediates:
>
> ```bash
> # keep only the first cert of a two-cert bundle (intermediate + root)
> awk '/BEGIN CERTIFICATE/{n++} n==1' bundle.ca-bundle > intermediates.crt
> ```

> **What's mandatory vs. hygiene:** the **leaf being first is mandatory** —
> the server matches its private key against the *first* cert in the file
> (Go's `tls.LoadX509KeyPair`, which Teleport uses, fails to load the
> keypair otherwise) and sends the remaining blocks verbatim as the chain.
> Including the root is merely wasteful: clients ignore a redundant anchor,
> so `leaf + intermediates + root` still works — it just adds ~2KB to every
> handshake and makes TLS scanners flag "chain contains anchor". Ship
> `leaf + intermediates` and both problems never come up.

## 7 — Create the Kubernetes secret

```bash
kubectl -n teleport create secret tls teleport-tls \
  --cert=chain.crt \
  --key=teleport.example.com.key
```

In the Helm values (all the values files in this repo are already wired this
way):

```yaml
acme: false
tls:
  existingSecretName: teleport-tls
```

### 7A — Publicly trusted CA

That's everything — usually. Do **not** set `existingCASecretName` for a
publicly trusted cert; the container's Mozilla bundle already has the root.
(Exception: a brand-new CA root — see the crashloop note below, and verify
against the image bundle *before* deploying.)

### 7B — Private/corporate PKI

The pods **do** need your CA — and the bundle you give them should be
**the image's own trust bundle plus your corporate root**, not the root
alone:

```bash
# Extract the trust bundle from the exact image you deploy:
CID=$(docker create public.ecr.aws/gravitational/teleport-ent-distroless:18.10.1)
docker cp $CID:/etc/ssl/certs/ca-certificates.crt image-ca-bundle.crt
docker rm $CID

# Append your corporate root and create the secret:
cat image-ca-bundle.crt corporate-root-ca.crt > ca.pem
kubectl -n teleport create secret generic teleport-tls-ca \
  --from-file=ca.pem=ca.pem
```

```yaml
tls:
  existingSecretName: teleport-tls
  existingCASecretName: teleport-tls-ca
  existingCASecretKeyName: ca.pem
```

(On OpenShift, [`03-openshift/values-corporate-pki.yaml`](03-openshift/values-corporate-pki.yaml)
already contains this tls block.)

**Why the CA secret at all:** at startup the Proxy Service verifies its own
configured cert chain against the *container's* trust store and exits
fatally if the chain doesn't terminate at a trusted root (`x509:
certificate signed by unknown authority`, pods in CrashLoopBackOff). A
corporate root is never in the container's Mozilla bundle.
`existingCASecretName` sets `SSL_CERT_FILE`, which Go's cert pool honors —
that's how the check passes. This check has existed since 2017; every
Teleport version behaves this way.

**Why the full bundle and not just your root:** `SSL_CERT_FILE`
**replaces** the Mozilla bundle for the pods' outbound TLS too. Root-only
boots the proxy but silently breaks every future outbound connection to
public endpoints — SSO providers (Okta/Entra), webhooks, plugins — with
`certificate signed by unknown authority`. Image-bundle + root keeps both
directions working. Since the bundle comes from the image, **rebuild this
secret when you upgrade Teleport**.

**What this does NOT do:** nothing for clients — the corporate root must
still be in the OS trust store of every workstation and every enrolled node
(see [`03-openshift/install-ssh-nodes.md`](03-openshift/install-ssh-nodes.md)).

> **Proxy CrashLoopBackOff: `unable to verify HTTPS certificate chain`** —
> the startup check above failed. Two causes, two fixes:
>
> 1. **Private/corporate PKI** and no CA secret → follow 7B above.
> 2. **Public CA whose root is newer than the container's bundle.** CA
>    trust bundles in server images lag: a recently established root (e.g.
>    SSL.com's 2022 roots vs. the Debian bundle in the Teleport image) may
>    be missing even though your laptop trusts it. CAs bridge this by
>    cross-signing the new root with an older established one — fetch the
>    cross-signed cert from the CA's repository and append it to
>    `chain.crt` (leaf → intermediates → cross-signed root). It acts as one
>    more intermediate: old-bundle hosts chain through it, modern clients
>    ignore it. This also fixes older *client* machines with dated bundles.
>    Verify before deploying:
>
>    ```bash
>    # extract the ACTUAL trust bundle from the image you deploy
>    CID=$(docker create public.ecr.aws/gravitational/teleport-ent-distroless:<version>)
>    docker cp $CID:/etc/ssl/certs/ca-certificates.crt image-bundle.crt && docker rm $CID
>    openssl verify -CAfile image-bundle.crt -untrusted intermediates.crt leaf.crt
>    ```

## 8 — Verify the deployed cluster

After the install (and DNS pointing at the proxy), from a client machine:

```bash
# 1. Trust + chain + SAN + expiry, all in one shot — must work with NO -k flag
curl https://teleport.example.com/webapi/ping | jq .server_version

# 2. What is the server actually presenting?
openssl s_client -connect teleport.example.com:443 -servername teleport.example.com \
  </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -ext subjectAltName -fingerprint -sha256

# 3. The fingerprint above MUST equal the cert in the secret:
kubectl -n teleport get secret teleport-tls -o jsonpath='{.data.tls\.crt}' \
  | base64 -d | openssl x509 -noout -fingerprint -sha256
```

If the fingerprints in 2 and 3 **differ**, something between the client and
Teleport is terminating and re-signing TLS (an edge-terminating ingress/
Route, or a corporate TLS-inspection appliance). Teleport multiplexes SSH,
gRPC, kube, and DB protocols over port 443 via ALPN — the web UI will look
fine through a TLS-terminating hop, but `tsh` will fail with errors like
`transport: authentication handshake failed: context deadline exceeded`.
Every hop must pass raw TLS through (on OpenShift: a **passthrough** Route —
see [`03-openshift/`](03-openshift/)).

## Renewal

Certificates expire; the secret doesn't renew itself. When you reissue:
rebuild `chain.crt` (intermediates may have changed!), recreate the secret,
and restart the proxy — it does not watch the secret for changes:

```bash
kubectl -n teleport delete secret teleport-tls
kubectl -n teleport create secret tls teleport-tls --cert=chain.crt --key=teleport.example.com.key
kubectl -n teleport rollout restart deployment/teleport-cluster-proxy
```

## Quick reference — the six things that must be true

| # | Requirement | One-line check |
|---|---|---|
| 1 | SANs contain the cluster name (+ wildcard for app access) | `openssl x509 -noout -ext subjectAltName -in chain.crt` |
| 2 | Full chain, leaf first, no root | `openssl crl2pkcs7 -nocrl -certfile chain.crt \| openssl pkcs7 -print_certs -noout` |
| 3 | Key matches leaf | pubkey sha256 of cert == key (Step 3) |
| 4 | Chain verifies to a trusted root | `openssl verify -CAfile root.crt -untrusted intermediates.crt leaf.crt` |
| 5 | **The server image trusts the issuing CA** — the proxy refuses to start otherwise | Public CA: `openssl verify` against the image's extracted bundle (Step 7A / crashloop note). Corporate PKI: the `teleport-tls-ca` secret from 7B |
| 6 | Clients trust the root & TLS reaches Teleport unterminated | `curl` ping with no `-k`; fingerprint compare (Step 8) |
